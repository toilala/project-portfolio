How My Slow Old Computer
Got Me Into GitHub Actions

I stopped waiting on my own computer and let GitHub build my Android app instead.

by Nischal Koiralanov 2026about 6 min

NOTE
01first one on the page

For a long time, I used GitHub for one thing: keeping my code. It also kept a history of my changes, so if I broke something, I could go back to a version that worked. That was all I did and wanted from it. Around that familiar routine sat tabs and settings with names like Actions, workflows, and runners. They looked important. They also looked like things I could safely leave to people who knew more than I did.

That changed when I started building oris, an Android music app. An Android app has to be built using a computer before you can install it in your phone, and I had to do that again and again to check whether my bug fixes worked. My computer is a little unfit for that kind of job. It can do it, but repeating it over and over became a hassle. Building my app locally took ages and failed far more often than it worked, and every time I was praying it would not run out of CPU or memory halfway. I spent a lot of evenings reading Gradle logs and hoping the next attempt would finish.

Finding out what the Actions tab does

After enough playing around, I started digging around to see if there was a better way. That is how I found GitHub Actions. I had no idea GitHub could give me a computer to run a build on. You write down a list of steps, and GitHub runs them on one of its machines when something you choose happens, like a push, or when you start the workflow manually.

For my app, those steps fetch the code, set up Java, build the app and run its unit tests. If the build succeeds, I get an APK, the file you install on an Android phone, which I can download from the run page. I think of it as my unpaid intern. I wrote the instructions once, and now it runs the build for me on a machine much faster than mine, without complaining.

It does not fix my mistakes, though. If the code is broken, the build still fails, and I still have to read the logs and that's expected. The difference is that I no longer have to rely on my computer to get a build done.

GitHub calls a set of instructions like this a workflow, and it can run automatically, so I never have to repeat those steps by hand.

The words are the hard part

Most of what put me off Actions was the vocabulary. A workflow is a set of instructions saved in a YAML file inside the .github/workflows folder in your repository. It starts when something happens, like a push, or when you run it manually. A workflow contains jobs. Each job runs on a runner, the machine doing the work, and contains a list of steps. Those were the words I needed to get started.

One thing I had to learn is that the machines used by my workflows are temporary. Each job gets a fresh one, and it is discarded afterwards. If I want to download a file after the job finishes, I have to save it as an artifact. That is how the oris APK gets to me. Artifacts do not last forever either: my workflows keep debug APKs for 14 days and release APKs for 7.

Why my app has four workflows

Over time, my app (oris) ended up with four workflows. One builds the app and runs the unit tests. One runs it in an emulator to check playback. One makes a signed release build and only publishes a release if I turn on the publish option when I start it. The last builds a signed release APK and launches it in an emulator for a quick smoke test. That last check is separate; it does not automatically stop the release workflow from publishing.

The signing key worried me too. A release APK needs to be signed, but I did not want to put a private key in a public repository. The release workflow reads the key and its passwords from GitHub Actions secrets instead of keeping them in the workflow file. Someone reading that file can see the secret names, not their values. That answered my initial worry, but it is not a reason to stop being careful: the workflow can access those secrets, so I still need to be careful about what code it runs and what it writes to logs.

Is it really free?

For the standard GitHub hosted runners I use with oris, yes. GitHub's documentation says those runners are free for public repositories, and oris is open source. Private repositories get an included amount of compute usage and storage based on the account's plan, with charges for additional usage. Larger runners cost extra, even for public repositories. There are usage limits too, so it is worth checking the current terms before relying on it.

For a project like mine, that means I can run builds, get the APKs and read the logs without paying for a more powerful computer just to build the app. That was a much more useful discovery than I expected from a tab I had been ignoring.

If you have been avoiding the tab too

Pick one boring thing you already do by hand, like building your app or running your tests, and set it up in Actions. You do not need four workflows to start. You will pick up the words as you go. I still have plenty to learn, but my builds which I have to do 10s of times a day no longer depend on my old computer, and that alone was worth opening the tab.
